# Wildlife Match — handoff для продовження роботи

Оновлено: 28 серпня 2026 року.

## Що переносити на інший ПК

Скопіюйте всю папку `WILDLIFE_MATCH_IMPLEMENTATION_PACK_V2`, а не лише `starter/`. У ній є готовий сайт, початкові вимоги, референси та скрипти перевірки.

Головний файл сайту:

```text
starter/index.html
```

## Поточний стан

Сайт реалізований на HTML5, CSS3, vanilla JavaScript і PHP без фреймворків та етапу збірки.

Готові сторінки:

- `starter/index.html` — головна сторінка з вісьмома секціями;
- `starter/wildlife-removal.html`;
- `starter/attic-cleanup-restoration.html`;
- `starter/entry-point-sealing-prevention.html`;
- `starter/privacy.html`;
- `starter/terms.html`;
- `starter/cookie-policy.html`.

Також готові:

- адаптивна ліва бренд-панель і мобільне меню;
- локальні WebP-зображення в `starter/img/`;
- чотири форми запиту;
- `handler.php` із серверною валідацією, CSRF, rate limiting і вкладеннями;
- non-JavaScript підтвердження форми;
- cookie consent без підключених аналітичних або рекламних скриптів;
- конфігурація, юридичні сторінки, README та облік зображень;
- скрипти та скриншоти QA в папці `qa/`.

## Важливі правила проєкту

- Wildlife Match — незалежна referral-платформа, а не підрядник.
- Провайдери незалежні; відповідь або доступність не гарантуються.
- Не додавати телефонні номери, телефонні поля, телефонні іконки чи телефонні посилання.
- Не вигадувати відгуки, рейтинги, нагороди, ліцензії, кількість провайдерів або завершених робіт.
- Не стверджувати, що Wildlife Match виконує, контролює, оцінює, інспектує або гарантує роботи.
- Не замінювати мозаїчні макети звичайними картками чи типовим блоком «текст + фото».
- Не використовувати градієнти, округлі картки, UI-фреймворки або зовнішні гарячі посилання на зображення.
- Усі зміни мають залишатися сумісними з HTML/CSS/vanilla JS/PHP без build step.

Повний порядок пріоритетів та вимоги містяться у файлах `01_LOCKED_DESIGN_SYSTEM.md`–`06_VISUAL_QA_CONTRACT.md`.

## Конфігурація перед публікацією

У `starter/config/site-config.js` потрібно замінити:

- `CONFIGURE LEGAL OPERATOR` — юридичне або публічне ім’я оператора;
- `hello@example.com` — корпоративна email-адреса;
- `CONFIGURE POSTAL ADDRESS` — поштова адреса;
- `CONFIGURE DESTINATION EMAIL` — клієнтське відображення адреси призначення, якщо воно потрібне.

У `starter/config/server-config.php` потрібно встановити реальну приватну адресу:

```php
const FORM_DESTINATION_EMAIL = 'requests@example.com';
```

Не покладайтеся на `site-config.js` для серверної маршрутизації пошти. `handler.php` використовує лише приватний PHP-конфіг.

## Локальний запуск

Потрібен PHP 8.1 або новіший із розширеннями `mbstring` і `fileinfo`, а також налаштований поштовий транспорт для фактичної доставки форми.

З кореня пакета:

```sh
php -S 127.0.0.1:8080 -t starter
```

Після цього відкрийте:

```text
http://127.0.0.1:8080/index.html
```

Не тестуйте форму через пряме відкриття HTML-файла: сесії, CSRF і PHP так не працюватимуть.

## QA та перевірки

Статичний аудит:

```sh
python qa/audit.py
```

Він перевіряє сім сторінок, обов’язкові файли, локальні посилання, H1, поля форм, заборонені фрази, телефонні артефакти, градієнти та локальні WebP.

Браузерний аудит:

```sh
node qa/browser-audit.mjs
```

Скрипт очікує локальний сайт за адресою `http://127.0.0.1:8765`. На новому ПК може знадобитися змінити імпорт Playwright і шлях до Chrome на початку файлів:

- `qa/browser-audit.mjs`;
- `qa/capture.mjs`;
- `qa/debug-overflow.mjs`.

Зараз там записані Windows-шляхи зі старого ПК. Альтернатива — встановити Playwright локально й замінити абсолютний імпорт на:

```js
import { chromium } from 'playwright';
```

Обов’язкові розміри перевірки:

- 1440×900;
- 1024×900;
- 390×844;
- 360×800.

Останній браузерний аудит пройшов для всіх семи сторінок на всіх чотирьох розмірах. Також пройшли перевірки мобільного меню, повернення фокусу, cookie persistence, локальних зображень, console errors і горизонтального overflow.

## Відомі обмеження останньої сесії

- На старому ПК не було PHP CLI, тому `handler.php` був перевірений статично, але реальне надсилання email не запускалося.
- Для end-to-end тесту потрібні реальна адреса призначення та працездатний серверний mail transport.
- QA-скрипти містять абсолютні шляхи до локального Node runtime і Chrome; адаптуйте їх на новому ПК.
- Значення оператора, email і поштової адреси навмисно залишені для власника сайту.

## Зображення

У `starter/img/` є 31 локальний WebP-файл. Вони згенеровані спеціально для цього проєкту та не залежать від зовнішніх URL.

Походження і стислий prompt set описані в:

```text
starter/IMAGE_CREDITS.md
```

Скрипт підготовки зображень:

```text
qa/process_assets.py
```

Він містить абсолютний шлях до каталогу з первинними генераціями на старому ПК. Готові WebP вже лежать у `starter/img/`, тому для звичайного продовження цей скрипт запускати не потрібно. Якщо потрібна повторна обробка, спочатку оновіть змінну `GEN`.

## Рекомендований порядок продовження

1. Скопіювати весь пакет на новий ПК.
2. Встановити PHP 8.1+, Python 3, Node.js, Chrome/Chromium і Playwright для повного QA.
3. Заповнити `site-config.js` та `server-config.php` реальними даними власника.
4. Запустити сайт через PHP.
5. Перевірити CSRF endpoint: `http://127.0.0.1:8080/csrf.php`.
6. Надіслати тестову форму без файлів і з одним JPG/PNG/WebP.
7. Перевірити JSON-відповідь, non-JavaScript confirmation flow і фактичну доставку листа.
8. Запустити `qa/audit.py` та браузерну матрицю.
9. Повторно зробити скриншоти після будь-яких візуальних змін і порівняти їх із `references/`.

## Перед фінальним деплоєм

- прибрати всі `CONFIGURE` і прикладні email-адреси;
- переконатися, що HTTPS увімкнено;
- перевірити серверні ліміти `upload_max_filesize`, `post_max_size` та сесії;
- налаштувати SPF/DKIM/DMARC для домену відправника або замінити `mail()` на затверджений серверний транспорт без зміни публічного API форми;
- перевірити політики після додавання будь-якої аналітики, реклами чи стороннього сервісу;
- повторити повну QA-матрицю.
